## User Scenarios & Testing _(mandatory)_

### User Story 1 - Install and configure once (Priority: P1)

As the sole user, I want an installed Moneydance extension whose settings and availability survive restarting Moneydance, so I do not have to load a script each session.

**Why this priority**: Persistent installation and unattended configuration are prerequisites for reliable delivery.
**Independent Test**: Install using the documented supported process, configure a synthetic book and destination, close and reopen Moneydance repeatedly, and verify the extension and settings remain available without reinstalling.

**Acceptance Scenarios**:

1. **Given** a supported Moneydance installation, **When** installation completes and Moneydance is restarted three times, **Then** the extension, its menu action and configuration screen remain available without reinstallation or manually loading a script.
2. **Given** the configuration screen, **When** the user saves the encryption password and required destination/authentication information, **Then** those settings survive restart, secret values are masked, and automatic delivery needs no further password entry in Moneydance.
3. **Given** incomplete or invalid settings, **When** the user attempts delivery, **Then** an actionable configuration error appears without publishing data or silently using another destination.
4. **Given** installation requires signing material, **When** the package is prepared, **Then** the documented supported signing process uses actual user-supplied material or material generated by prescribed tools; generated-looking certificate text is never substituted.

### User Story 2 - Publish a protected snapshot on demand (Priority: P1)

As the user, I want a Moneydance menu action that exports, encrypts and uploads my latest data to the configured Azure Blob Storage location.

**Why this priority**: This provides a controllable end-to-end workflow and a way to retry a failed automatic delivery.
**Independent Test**: Use the menu with a controlled book, retrieve the published encrypted snapshot, unlock it in the viewer, and compare the financial data with the source.

**Acceptance Scenarios**:

1. **Given** valid settings and a stable source book, **When** the menu action runs, **Then** a complete financially validated snapshot is encrypted with the configured password and published to the configured location, with a clear success result.
2. **Given** an export, encryption or upload failure, **When** the operation finishes, **Then** its failing stage and corrective guidance are visible, no plaintext is uploaded, and the last successfully published snapshot remains usable.
3. **Given** an operation already in progress, **When** the menu is selected again or shutdown begins, **Then** deliveries do not overlap or allow an older result to overwrite a newer result.
4. **Given** credentials are expired or approaching expiry, **When** the user navigates Moneydance, **Then** plain expiry warning text is shown in the status bar and directs the user to **Extensions > Snapshot Settings**; selecting that menu action opens the Azure Storage configuration screen with renewal instructions. The status text itself need not be clickable.

### User Story 3 - Publish automatically when Moneydance closes (Priority: P1)

As the user, I want closing Moneydance normally to publish the current snapshot without running an additional script or application.

**Why this priority**: Automatic delivery is the principal workflow requested in Part 2.
**Independent Test**: Change a controlled book, close Moneydance normally, reopen it, and confirm that the newly published snapshot reflects the final saved source state and that delivery status is available.

**Acceptance Scenarios**:

1. **Given** configured delivery and a normal application exit, **When** Moneydance closes, **Then** the extension completes export, encryption and publication using the final saved book state while the required source data is still available.
2. **Given** networking is unavailable during exit, **When** delivery fails or reaches its bounded timeout, **Then** Moneydance is not left waiting indefinitely, the previous published snapshot remains usable, and a sanitized failure result is shown on the next launch.
3. **Given** a canceled exit or duplicate lifecycle notification, **When** the application remains open or repeats the notification, **Then** the extension does not publish a conflicting duplicate or report an unfinished operation as successful.

### User Story 4 - Unlock the existing viewer (Priority: P1)

As the user, I want to enter my encryption password on the desktop or Pixel 8 and use the same balances, register and search interface with the decrypted data.

**Why this priority**: Encrypted delivery is useful only if the intended viewer can unlock the published snapshot.
**Independent Test**: Publish a controlled snapshot, open the real-data viewer on desktop and Pixel 8, enter correct and incorrect passwords, and exercise existing viewing behavior.

**Acceptance Scenarios**:

1. **Given** real-data mode, **When** the page loads, **Then** the viewer prompts for a password and does not render financial data before successful decryption and snapshot validation.
2. **Given** the correct password and an intact supported encrypted snapshot, **When** unlocking succeeds, **Then** existing balances, history, searches, future disclosure and the localized "As of"
   footer behave as in Part 1.
3. **Given** a structurally valid, supported encrypted file, **When** authentication fails because of an incorrect password or altered ciphertext, **Then** the viewer displays a safe error and permits another password attempt without downloading again. The message need not distinguish a wrong password from corruption. Unsupported or structurally invalid envelopes display a terminal error requiring reload. Neither case displays financial data.
4. **Given** explicit test=true mode, **When** the viewer loads, **Then** the existing unencrypted synthetic dataset loads without a password prompt and is visibly identified as test data.
5. **Given** an unavailable real snapshot or invalid decrypted snapshot, **When** loading fails, **Then** the existing explicit error/no-automatic-fallback behavior is retained, including the missing-real-file link to test data.
6. **Given** real-data mode, **When** the page loads and the user stored the password in a common commercial password manager or the browser, **Then** the password should prepopulate in the password textbox, according to that password manager's normal autofill workflow.

### Edge Cases

- Missing credentials, blank encryption password, denied upload access, malformed destination and expired credentials must fail visibly without publishing plaintext.
- Interrupted upload or exit must not replace a complete snapshot with a partial object. If the remote result is uncertain, report uncertainty rather than assert failure or success incorrectly.
- Wrong password, unsupported encryption format, truncated ciphertext, tampering and invalid decrypted financial data must never produce misleading balances.
- Forced termination, process crash or power loss cannot be represented as a guaranteed successful normal-exit export.
- Password changes affect subsequent exports; the currently published file still requires its original password until replacement succeeds. No password recovery service is included.
- Encryption passwords, upload credentials and signing keys are separate secrets and must not be accidentally exposed through status, logs, source control or the website.
- Multiple open books or switching books must not send an unintended book to the configured destination. Delivery is scoped to the explicitly configured book.
- Warning boundaries include exactly 30 days before known expiry and already-expired credentials. Unknown expiry is displayed as unknown, not as non-expiring.
- A page restored from the browser cache retains its page-session data and cutoff; a fresh page load requires unlocking again. Clearing or ending the page session does not retain the password or decrypted records in browser storage.

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: Provide an actual persistently installed Moneydance extension with a delivery menu action and configuration screen. Closing and reopening Moneydance MUST NOT require reinstallation or manual script loading.
- **FR-002**: Preserve the existing exporter's financial semantics and full included history, USD cent precision, account relationships, compact balances and source read-only behavior. The export logic MUST remain Moneydance-compatible Jython 2.7; this user-required constraint is not permission to replace it with a standalone incompatible exporter.
- **FR-003**: Persist book-scoped configuration sufficient for unattended delivery: encryption password, Azure Blob Storage destination and required authentication information. Protect stored secrets, mask them in normal UI, and keep upload credentials and signing private keys out of the web viewer.
- **FR-004**: The menu action MUST perform export, validation, AES encryption and upload as one ordered operation, with clear progress and a sanitized final result. An earlier-stage failure MUST prevent later publication.
- **FR-005**: Normal Moneydance exit MUST trigger the same delivery operation for the configured book's final saved state. The operation should add no more than 60 seconds to the Moneydance shutdown process (documented default for review); do not depend on accessing an already-closed book or launching a script manually afterward.
- **FR-006**: Serialize delivery requests and handle repeated exit notifications without conflicting uploads, lost error status or older-over-newer publication.
- **FR-007**: Encrypt real financial data before remote publication. Protect both confidentiality and integrity; wrong passwords, tampering and unsupported encrypted formats MUST fail closed. The AES requirement is explicit in the brief; cryptographic construction and interoperable file format are planning decisions.
- **FR-008**: Publication MUST leave readers with a complete previous or complete new encrypted snapshot, never a partial replacement. Preserve the last good publication on a failed attempt; report uncertain remote outcomes accurately. Do not deliberately leave plaintext staging files behind after the operation.
- **FR-009**: Prefer authentication without a user-maintained expiring secret. If an expiring configured secret is required, its issuance-to-expiry lifetime MUST be 22–24 months. Short-lived automatically renewed access tokens are not the user-maintained secret governed by this requirement. If the supported service policy cannot meet the requirement, report the incompatibility for user decision rather than silently shorten the lifetime.
- **FR-010**: For a configured expiring secret, show its known expiration and warn beginning 30 days before expiry on startup, configuration access and delivery attempts. Show plain status-bar warning text directing to **Extensions > Snapshot Settings**, whose menu action opens Azure configuration and renewal instructions; status text need not be clickable. Permit replacement without reinstalling. Do not claim unknown expiration is non-expiring.
- **FR-011**: Persist only sanitized last-operation status needed to show shutdown success/failure on the next launch; identify export, encryption or upload as the affected stage. Permit manual retry without requiring restart or reinstall.
- **FR-012**: Installation/signing instructions MUST follow methods verified for the actual Moneydance runtime. The AI MUST NOT invent certificates, keys, signatures or signing success. If required, obtain genuine material from the user or generate it with prescribed command-line tools and verify actual outputs. Whether signing is necessary MUST be established, not assumed from the brief's tentative wording.
- **FR-013**: In real-data mode, prompt for the decryption password, unlock and validate the encrypted snapshot before rendering any financial data. Do not accept unencrypted real-data input as a silent fallback.
- **FR-014**: Keep the browser password and decrypted records in page-session memory only by default. Allow password correction against the already-downloaded encrypted file. Account changes, paging and search MUST NOT redownload the snapshot or change financial values.
- **FR-015**: Preserve all accepted Part 1 viewing behavior, including source running balances, descendant memo/amount search, hidden-account contributions, future disclosure, test-mode selection, no All Accounts balance and the export-time footer. Encryption MUST NOT redefine exportDate or the device-local page-load cutoff.
- **FR-016**: Keep the synthetic test dataset unencrypted and password-free under explicit test=true. Retain the test-data indicator and no-automatic-fallback behavior. The brief's hard-coded synthetic password alternative is unnecessary unless plaintext test mode proves infeasible and is reconsidered explicitly.
- **FR-017**: Use the existing supplied-location viewer arrangement for encrypted delivery; do not expose upload authorization to the viewer. Provisioning instructions must identify the required read access and destination settings without claiming ciphertext hosting makes upload credentials safe to expose.
- **FR-018**: Document and verify installation persistence, normal-exit delivery, failed-publication preservation, desktop/Pixel decryption, and full-history performance using synthetic tests followed by controlled real-data checks. Keep private records and secrets out of shared evidence.
- **FR-019**: The web password input MUST be compatible with Keeper Security, LastPass, and the iOS Safari built-in password managers. "Compatible" specifically means that it supports each manager’s normal autofill workflow without requiring manual password typing, including automatic filling where permitted.

### Key Entities

- **Extension installation**: Installed identity, supported Moneydance runtime, menu/configuration availability and any genuine signing material needed for installation.
- **Delivery configuration**: Configured book, destination, protected encryption password, upload authorization and any known credential expiry.
- **Snapshot**: Existing financially validated export, preserving its source export instant and full included history.
- **Encrypted publication**: A complete protected snapshot at the configured remote location, unlockable by the intended viewer.
- **Delivery attempt**: Manual or normal-exit trigger, current stage, completion result and sanitized timestamp/status.
- **Viewer unlock session**: One downloaded encrypted snapshot, entered password, unlock outcome and in-memory validated viewing data.

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: Across three normal close/reopen cycles after a single installation, the extension and saved settings remain available, and each configured exit produces a verifiably current publication without reinstallation or manual script loading.
- **SC-002**: Both manual and exit-triggered delivery preserve 100% of the agreed source reference entries, relationships, amounts and balances after successful unlocking; source financial records remain unchanged by delivery.
- **SC-003**: Every tested export, encryption, authorization, network and interrupted-publication failure produces a truthful result and leaves the prior successful publication usable; no tested operation publishes plaintext real financial data.
- **SC-004**: Correct passwords unlock controlled publications on desktop and Pixel 8; all tested incorrect-password, corruption and tampering cases reveal no financial records. Password correction does not cause another download.
- **SC-005**: In five full-history Pixel 8 trials, loading, decryption, validation and first usable balances/rows together finish in under ten seconds per trial, excluding time spent waiting for the user to enter the password. Record the password-entry exclusion and include all machine processing and download time. Twenty representative searches remain below two seconds each, including debounce.
- **SC-006**: The user can install/configure once, publish manually, close/reopen with automatic delivery, and unlock the viewer using documented instructions. Expiry boundary tests show the warning at 30 days remaining and after expiry; recorded credential lifetimes meet FR-009 or the no-expiring-secret preference is satisfied.
- **SC-007**: The existing synthetic viewer loads without a password and passes all applicable Part 1 acceptance scenarios; real mode never silently falls back to plaintext or test data.
- **SC-008**: Export, Encryption and Upload trials finish within 60 seconds. The user measures this by ensuring the export process adds no more than 60 seconds to the overall Moneydance shutdown process. The process shows the correct sanitized result on next launch.

## Assumptions

### Scope and defaults for review

- This is the personal, single-user, USD read-only workflow from Part 1. It explicitly advances previously deferred extension installation, shutdown automation, encrypted Azure delivery and browser unlocking. Investment presentation, net worth, transaction entry, multiple users and a redesign remain excluded.
- Target the user's existing Windows Moneydance installation and Pixel 8/desktop/iOS Safari browsers. The last verified source runtime was Jython 2.7.2 / Moneydance build 5253; compatibility must be checked on the actual installation during implementation.
- One explicitly configured book and one current publication location are sufficient. Multi-book routing, remote version history, background sync queues, automatic retries after restart and password recovery are not required.
- Normal application exit is the automatic trigger; merely switching/closing a book is not an additional publishing trigger. A forced kill or power loss is outside the success guarantee.
- Capture may run once after the save associated with closing the configured book, before application exit is known. The user works in one book and accepts a capture delay on an occasional book switch. Ordinary saves must not trigger capture. Only application exit triggers automatic publication; opening another book invalidates the detached candidate. Never publish another book's data to the configured destination.
- Desktop configuration remembers the password because automatic exit delivery must be unattended. The viewer itself does not persist passwords; user-controlled browser/password-manager storage is supported.
- A 30-day warning window, 60-second maximum shutdown delivery wait, sanitized next-launch delivery status, serialized attempts and preservation of the last good publication are defaults selected to make failure behavior concrete.
- Existing hosting is user-provisioned. Configuring access and delivery to that destination is in scope; constructing a new website hosting platform, CDN or infrastructure-management system is not.
- No real credentials, certificate generation, cloud writes or installation are performed by this specification command.

### Planning and verification dependencies

- Verify Moneydance's supported persistent extension packaging/registration and signing process from authoritative sources. Do not mistake session-loaded scripts for installed extensions, assume a signing certificate is required, or invent a signing identity.
- Verify a supported lifecycle point that permits final saved-state capture and completion before source teardown. Verify the proposed 60-second shutdown bound with tested success/failure behavior; a lifecycle that cannot meet FR-005 is a blocker, not permission to claim completion.
- Establish the AES encryption format, password derivation, integrity protection and interoperability using proven facilities compatible with both required runtimes. Validate secret storage and temporary-file handling rather than assume obscuring a setting protects it.
- Select supported Azure authorization and viewer read-access arrangements. Verify lifetime constraints and service policy for any user-maintained expiring secret. Do not promise that an unverified authentication option supports 22–24 months.
- Measure the combined full-history load/decrypt workflow; Part 1's passing plaintext load times do not establish this feature's target.
- Constitution v1.1.0 applies. Its deferred-work boundary is explicitly revisable and Part 2 advances that scope; no principle exception is requested. Dependency adoption still requires evidence and justification, including transitive footprint. Technical feasibility gates remain open for planning, not hidden claims of completed research.
