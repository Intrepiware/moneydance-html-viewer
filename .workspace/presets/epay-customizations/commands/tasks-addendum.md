## ePay manual acceptance policy — task generation

Apply these requirements during task generation, not as an optional follow-up. They specialize generic core statements that tests are optional or independently testable stories may run concurrently. Explicit user instructions and the adopted project constitution still govern; identify any conflict instead of silently overriding either.

1. Preserve the user-approved story order. Give every story at least one explicit manual acceptance task unless a justified story-level exception is recorded. Cover the main happy path, relevant failures and material edge cases without redundant repetition. Low-impact documentation-only work can have a justified exception; do not invent application tests.
2. Use exactly `- [ ] [Manual Test] Tnnn [USn] ...`. Manual tasks belong in their story's execution section. Keep IDs unique and stable when inserting tasks; a larger ID can appear before a smaller ID. Explain that `[P]` permits independent work only within an eligible story/phase, never across a blocked story boundary.
3. Each manual task identifies reproducible setup, actions, expected results and its evidence location in the feature's `acceptance.md`. For unusual but feasible setup, link detailed steps in `quickstart.md` or a focused guide. Include tasks to deliver necessary synthetic fixtures, routes or tools before the manual check. Do not assume unavailable devices, accounts or credentials exist.
4. Add an explicit checkpoint after each story: implementation of any later story, including its tests and fixtures, waits for all required manual tasks in every preceding story to pass. Retain dependencies that impose additional restrictions. Planning later stories and fixes/retests in the current story may continue.
5. State how justified omissions work: record scope, obstacle, uncovered behavior and alternative evidence or remaining gap. Unrun checks, failed checks or unavailable required equipment are not exemptions. A justified story exception satisfies the coverage requirement but is not a test pass; honor any constitution-required approval for exceptions.
6. Create an initial feature `acceptance.md` with a section per story and fields for task ID, pending/pass/fail status, tester, date, environment, expected/observed results and evidence links. Resolve `acceptance-template` using the project's existing template resolver when available. If that optional template cannot be resolved, create the same minimal structure directly. Do not install tooling just to resolve it. Never overwrite existing results, user notes, defects or retests.
7. Before finishing, audit story coverage, dependency order, manual setup deliverables, evidence paths and unique IDs. Report genuine gaps without fabricating fixtures or acceptance. Preserve existing checked tasks only when their evidence still covers unchanged requirements; explain any checks that need a retest after changed behavior.
