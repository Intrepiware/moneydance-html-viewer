You **MUST** consider the user input before proceeding (if not empty).

## Goal

Help the user understand the highlighted text by creating a code "sketch," so he can see the change and make informed predictions about what the AI will do when it executes the given instruction.

The user typically invokes this skill when he is reviewing a design document generated by AI-driven development (AI-DLC or spec-kit). Both frameworks instruct the AI to use concise language, which can lead to dense prose with several ideas crammed into a single sentence. The user reviews design documents to predict what the AI will do when given permission to execute; the dense language makes these design documents hard to read and predict the AI's behavior.

## Operating Constraints

**User MUST git commit/stash/stage all uncommitted work**. If the user has unstaged work when invoking this skill, the agent must advise the user to stage, stash or commit his work before running the skill. The user MUST comply or state that he accepts the risk of overwriting his uncommitted work.

This skill may be used with either user-highlighted text in a design document or a direction in the chat window.

## Proof of Concept

The agent should create the smallest possible change in the actual codebase to demonstrate to the user the change proposed by the design text. The agent should treat this change as temporary, and expect the user will undo (git reset) the change after he understands the proposal.

## Execution Steps

Follow these exact execution steps to create the proof of concept:

1. Verify the user has highlighted a section of a design document or provided a direction in the chat window. If neither is provided, provide an explanation how to use this skill and exit with no additional action.

2. The agent MUST explain that it will apply the smallest possible change to the codebase to demonstrate the change.

3. The agent MUST check if there is unstaged changes in git. If there are, the agent MUST **STOP** and advise the user to stage, stash, or commit the work before applying the change. The user MAY override this warning and accept the risk that temporary proof-of-concept code will get mixed with unapplied changes.

4. The agent MUST apply the change in a place that 1) makes the change as small as possible, and 2) allows the user to extrapolate what the change will look like when it is actually applied.

### Guidelines for the Proof of Concept code

- The change should be as small as possible, with the following caveats:
  - Clarity of the explanation should always take precedence over brevity.

  - For changes that will apply to multiple places in the codebase, the user may request the change applied in a place that will violate the "smallest change possible rule." This rule may be waived to respect the user's request.

- The change MUST use the same programming language as the code it is updating. Do not insert Python code into a C# function block, for example.

- The code DOES NOT need to actually function, build, or pass unit tests.

- The change MUST prioritize illustration and explanation quality over everything else.

- The proof-of-concept MAY use pseudo-code, call non-existent descriptive functions (e.g., `SendEmail()`), or have commented descriptions of code (e.g. `// Process the file here`)

- If the highlighted text describes applying a change to multiple places, the agent MUST only apply the change in one place (unless the user requests otherwise). For example, if the plan text describes adding a method to an interface, only add the method to ONE implementation of that interface.

- If practical, the code should follow the directions in the `.github/copilot-instructions.md` file and the `.specify/memory/constitution.md` file (if the user is running spec-kit). If following those rules will result in unnecessarily lengthy/verbose code, or substantially affects clarity, this rule may be waived with an explanation in the chat window.
